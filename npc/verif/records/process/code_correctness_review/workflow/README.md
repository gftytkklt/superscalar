失效关系须在原Make依赖中保证，不能要求用户额外clean绕过。

<a id="batching"></a>
## 修复批次的组织

来源：用户2026-10-18“逐项修改与验证、成组验收与确认、同类工作连续对话”明确授权，替代此前“小批次”的过窄解释；不改变其他业务 Milestone/Phase。

1. 一个工作单元为一个自适应修复组，不设固定两项停点。agent从既有队列选择已批准范围内、契约明确、依赖就绪且共享代码背景/调用链/验证环境的问题；4～8项仅作参考，不凑数、不设数量硬上限，复杂问题单独处理。不重排总计划或另建调度框架。
2. 开始前简列本组ID、修改边界和共同验收目标；满足既有确认/提交门槛且属于授权范围即直接实施，不另设准备报告、启动Prompt或重复批准。逐项最小修改并及时定向验证，每个CCR-F保留结论和证据，不在完成一两项后暂停。
3. 未决契约、新能力和超出已确定边界的实施停止；仅当阻塞项未留下影响其他项的修改、且依赖明确独立时继续组内其他项。失败不得带入后续验证后宣称整组通过；未完成/NotRun单列。
4. 正常停点为整组完成：核验最终组合状态，共享报告/环境并统一收尾，等用户确认和commit；不自动串行下一组、不扩大提交范围、不push。后续改动影响前项时重跑相关用例。
5. 唯一下一入口仍在TASK_QUEUE，记录范围/候选与选择依据、必读资料、依赖门槛、逐项及共享验收、停点。“继续”先恢复当前未闭合工作；已闭合且门槛满足时由agent选择并执行下一自适应组，无须用户指定编号。其他索引仅引用此入口。

默认可在同一对话继续相关修复组；组完成或commit本身不强制换对话。用户2026-10-20明确要求：每次提交落档都评估上下文长度与任务相关性，并明确提醒是否建议新对话；按[AGENTS“每轮执行与提交收尾”第6条](../../../../../../AGENTS.md)执行，不虚构上下文占比、不将建议增为额外审批。按变化增量检查状态并维护现有恢复入口；质量确已受影响时按WORKFLOW_POLICY §6停点处理。真实待决策略不能由“继续”推定裁决。

## 定向验证与真实回归

承接原 AGENTS “继续”第 6 条及用户 2026-10-17 的回归范围澄清：
验证采用少量有区分力的正常/失败场景，重点拦截错误与虚假 PASS，不扩展为通用 runner 或庞大协议。
复用已有反例、可靠runner和隔离环境，不为每个小修复重建框架/庞大矩阵；每次检查实际执行、退出码和有效结果。runner、执行链或相关配置变化时补对应判据故障验证。
真实回归按修改模块和依赖影响选择；未受影响部分可不测，host/fake 不能替代受影响功能的真实 guest 验证。

真实消费者包括 CPU-tests 全集、RT update/run 到 msh、nanos 三前台切换及后台 hello；不要求每批全部执行。
共享修改须覆盖受影响消费端，不能仅按消费端文件未变免测；记录选测依据和未测理由，无 GUI 不免除受影响功能的真实 guest。
这里的 update/run 是生成器变更后的验收步骤，不新增日常运行必经步骤；沿用各平台已有入口语义。

## 修复测试代码与证据的提交范围

来源：用户2026-10-18明确要求，修复相关测试代码只提交必要部分，也可不提交。

1. 验证执行要求不变；测试代码是否入库单独判断。仅有长期回归价值、可维护且适合现有测试入口的最小用例/脚本才随修复提交；没有必要时不提交测试代码，由agent筛选并说明，无须另设确认轮。
2. 一次性host/fake夹具、工具包装、采集脚本、生成的C/h/mk、日志/JSON不因后缀可跟踪就批量入库。必要的最小测试源与文字见证可保留；镜像、截图、编译产物及整份生产源码快照按[产物清理规则](#artifact-cleanup)在验证完成后删除，不再默认永久留在local。提交前核对暂存清单，按需使用仅作用于本批记录目录的忽略规则防止误加。
3. 修复报告保留命令、结果、限制及本地证据入口，继续更新records索引、当前状态和唯一下一入口；不以减少测试代码提交量为由减少必要验证，也不从commit推定本地证据已备份。默认不追溯清理历史已跟踪测试或改全仓跟踪规则；用户明确授权追溯清理时，定向分类、仅移出冗余文件的跟踪并保留本地原文件和字节，不改写历史commit。

<a id="framework-repair-archive"></a>
## 框架与 OS 组件修复的文档归档（2026-10-20起）

来源：用户2026-10-20要求在各问题验收文档直接保存 newlib 等框架/OS 组件修复前后 diff，并结合代码语句解释功能实现，随后明确要求固化进当前工作流。首次补齐范围及核验示例见[归档盘点](../framework-diffs-20261020/README.md)。本节是后续相关 CRP 修复完成及提交收尾的必备要求。

1. **适用范围与位置**：newlib/libos、Navy 构建、nanos-lite、AM/klib、RT BSP/集成及 am-kernels 等框架/OS 组件的实际修复，均在对应 CCR-F 验收报告正文内嵌 diff；根仓已跟踪的相关文件也适用。共享报告须标清每个问题对应的文件/修改；跨仓库分别列明。不能只链接本地忽略的 patch、嵌套 commit 或另建总表替代原报告内容。
2. **差异与版本**：以本批实际修复前后源码生成可复制的 unified diff，逐文件保留全部修复 hunks 及必要上下文，不用省略号代替代码。注明所属仓库、相对仓库根的路径、旧/新完整 commit；尚未提交的新源注明工作树状态、日期和 SHA256，不虚构 commit。未跟踪旧源或首次入库文件须保留真实旧基线的来源、SHA256 和修复补丁，不把 Git 的整文件新增当作实际功能修改。这里的旧版本是本批修复前版本，不默认是框架原始上游版本。
3. **结合语句解释实现**：围绕具体条件、取参、计算、拷贝、返回或发布语句说明原错误、修改后的执行顺序及实现的功能；按实际涉及内容说明边界、失败返回/状态保持、所有权和调用链影响。保留未改契约、未测范围及已知限制；部分修复只说明已落地部分，撤回候选和未修问题不得混作最终实现。
4. **归档核验**：在本组最终源码和既有验收身份固定后，核对每个内嵌 diff 与实际提交差异或已验收工作树/补丁一致。在隔离临时目录从注明的旧版本正向应用，结果须逐字节等于新版本；反向应用须恢复旧版本，同时核对问题/文件覆盖、相对路径和报告链接。记录真实核验结果；缺失旧基线或身份不符时明确列出缺口并按现有 Guard 处理，不能编造差异或宣称归档完成。此项文档核验不代替既有功能验收，也不要求无故重跑已验收测试。
5. **清理与历史**：在本批归档完成且核验通过后，才按[产物清理规则](#artifact-cleanup)删除可再生生产源码副本；保留必要基线身份和补丁。原样 diff 中的空上下文行、历史空白与 Makefile tab 应保持，空白检查告警必须逐条确认仅来自这些证据字节，不全局关闭检查或把正文错误一并豁免。既有验收报告以追加说明补充，不改写历史结论/manifest；新增内容引起的旧文档哈希变化以附记解释。
6. **提交与职责**：把必要的内嵌 diff 和说明随对应报告纳入根仓文档提交，更新 records 索引；源码仍按实际根/嵌套仓库分别归属，不为归档强行跟踪整个框架库或顺带纳入既有 mode 噪声。核对根文档与各仓源码的真实提交状态并分别记录；文档提交不代表嵌套源码已提交、生产结果获确认或忽略资产已备份。本要求不新增 commit/push、下一单元或软件安装授权，沿用原停点。

## 验证完成后的产物清理（2026-10-19起）

用户明确要求：本记录树的大镜像、截图等在完成验证后直接删除；旧实现通过 Git 对应版本重编译复现，不全部保存在本地。此要求覆盖[测试证据提交范围](#test-artifacts)及历史报告中“镜像/截图/构建树默认本地保留”的旧约定；不删除历史结论，不改写既有 manifest 或 Git 历史。本次已授权清理整个 `code_correctness_review` 中完成验证的历史产物，不需要逐文件再问；范围不延伸到主工程、真实 ramdisk、外部资源或进行中的验证。

1. 每次修复/提交收尾先完成必要验证、目视检查和结果记录；确认相关进程已结束，再清理磁盘夹具、镜像/ELF/可执行文件、对象/库/预编译头、波形、截图及隔离构建目录和可从 Git 重建的生产源码副本。不能在验证过程中先删其输入；不以清理替代验收。
2. 保留报告、实际命令/退出码/结果、配置和源码/产物身份、必要最小测试源及补丁。复现旧行为应明确 Git commit/父版本、配置差异、工具/构建命令与临时盘生成方法，从相应 Git 版本重建；未提交的新实现保留必要 patch。正式输入在工作区外时记录来源/哈希/已有配方，不另留整份历史镜像。截图删除前把实际目视观察和限制写入文字结果；其哈希仅作当时身份记录，不声称删除后仍可查看原图。
3. agent可使用[清理脚本](cleanup_artifacts.py)先盘点再应用：默认只生成清单，`--apply`删除/压缩。固定限定此记录树、不跟随目录symlink、不改写Git；保留文字证据和配置，较大原始日志无损gzip并校验解压哈希，权威coverage/jsonl矩阵不当编译垃圾删除。该脚本是agent收尾工具，不新增Make选项或用户日常必经步骤；有特殊未完成资料时先缩小清理范围，不机械执行。
4. 删除前落路径/字节/哈希/类别清单，删除后记录实际数量/空间与剩余产物终检。历史manifest保持当时清单，追加指向清理回执解释预期缺失；恢复/提交检查须合并清理回执，不能因预期删除报损坏，也不能继续宣称旧镜像可直接复用。大日志的新入口为同路径`.gz`，可按需流式读取。
5. 提交前复核只包含必要源码/回归测试/文档与授权的已跟踪产物删除，不误加新编译文件；若收尾后重测，验证结束再次清理。本要求不自动授权commit/push、下一批Start或删除源码/报告等非产物资料。

本次初始清理及再生入口见[F0009交付](../crp-f0009/README.md#artifact-cleanup-20261019)；以后每批在自己的报告附清理结果，不新建重复阶段或保留全量构建副本。

<a id="state-closeout"></a>
## 批次留档与状态承接

1. 每个 CCR-F 分别记录修改/未修、失败语义、验收证据与限制；涉及框架/OS修复时须完成[内嵌diff与实现说明归档](#framework-repair-archive)。报告留在对应 records 目录，更新 [process 索引](../../../README.md)。历史审阅台账与完成快照保留，不能用历史“未修”截面覆盖当前进展。
2. CURRENT_STATE 更新当前批次、最后完成动作、工作文件、风险及完成/确认/提交状态；Next Action 只指向 TASK_QUEUE 的唯一入口。TASK_QUEUE 同步本批状态，并按上方合批规则维护未来批次的范围、资料、门槛、逐项/共享验收和停点。
3. CHANGELOG_AGENT 按全局持久化规则追加实际完成或补充回执；管理维护只记维护结果，不伪造业务 Phase Completion。DECISIONS 仅新增长期技术裁决时更新，DOCUMENT_INDEX 仅重要导航变化时更新。
