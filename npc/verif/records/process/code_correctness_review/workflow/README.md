# CRP 代码正确性修复执行规则

<a id="scope"></a>
## 适用范围与入口

本文件是独立 CCR 后续 CRP 修复的现行任务规则，承接用户 2026-10-17/18 已明确的约束。
2026-10-18 按用户要求从 AGENTS.md / WORKFLOW_POLICY 迁入，保持原授权、验收与停点；不推广到其他任务。
全局授权、Guard、生命周期和提交规则仍见[AGENTS](../../../../../../AGENTS.md)与
[WORKFLOW_POLICY](../../../../docs/WORKFLOW_POLICY.md)。

- 修复准入、原分组与历史回执：[REPAIR_AND_REGRESSION](../REPAIR_AND_REGRESSION.md)及其引用的最终修复方向。
- 当前状态：[CURRENT_STATE](../../../../../../.agent/CURRENT_STATE.md)；唯一未来批次：[TASK_QUEUE / CRP Next](../../../../../../.agent/TASK_QUEUE.md#crp-next)。本文件不保存第二份 Next。
- 恢复时先执行全局 Guard，再读取本文件和队列列出的问题/证据；本规则本身不授权实施、提交或改变 CQ。

<a id="build-interface"></a>
## 构建接口与用户流程

来源：用户 2026-10-17 明确约束，原 AGENTS 全局规则第 6 条、WORKFLOW_POLICY §5。
代码正确性修复原则上不新增或删除 Makefile 选项、目标和用户执行流程，也不增加日常运行的必经步骤；确与功能正确性冲突时，说明具体依据并按既有裁决规则处理。

<a id="batching"></a>
## 修复批次的组织

来源：用户2026-10-18明确，修改批次可以是单个问题，也可以是相近的一批问题。

1. “继续”的一个工作单元指一个有明确边界的修复批次，可包含一个或多个既有问题ID。agent按模块/调用链、共同根因、契约及依赖选择合适的小批次，优先复用实现与验证，避免机械地一问题一轮；常规合批不需要额外确认。
2. 合批需各项契约明确、依赖/授权门槛相容、变更及验证成本可控；逐项列出ID、修改范围、失败语义和验收，同时选择能覆盖批次影响的共享真实回归。每个问题分别记录已修/未修与证据，不能从批次整体PASS推定所有项通过。
3. 不因合批跨越已规划Phase的确认/commit门槛、纳入未批准能力或默认裁决CQ。批内出现真实未决项时，按实际依赖拆开；不将独立项全部阻塞，也不把无关问题仅按编号/严重度凑成一批。
4. 唯一下一入口在TASK_QUEUE记录批次问题集合、选择依据、必读资料、依赖/门槛、逐项及共享验收和停点；本批统一收尾后停止，获用户确认/commit及后续授权再进入下一批。其他索引仅引用该入口。

在已批准修复主线内由 agent 维护拆分、排序和每轮范围，不全量重排问题或另建调度系统；
“继续”仍只执行已落档且满足门槛的一个单元。真实待决策略可先完成必要分析，不能由“继续”推定裁决。

<a id="validation"></a>
## 定向验证与真实回归

承接原 AGENTS “继续”第 6 条及用户 2026-10-17 的回归范围澄清：
验证采用少量有区分力的正常/失败场景，重点拦截错误与虚假 PASS，不扩展为通用 runner 或庞大协议。
真实回归按修改模块和依赖影响选择；未受影响部分可不测，host/fake 不能替代受影响功能的真实 guest 验证。

真实消费者包括 CPU-tests 全集、RT update/run 到 msh、nanos 三前台切换及后台 hello；不要求每批全部执行。
共享修改须覆盖受影响消费端，不能仅按消费端文件未变免测；记录选测依据和未测理由，无 GUI 不免除受影响功能的真实 guest。
这里的 update/run 是生成器变更后的验收步骤，不新增日常运行必经步骤；沿用各平台已有入口语义。
来源：[回归契约](../crp-f0052/README.md#product-regression-contract-20261017)、
[范围澄清](../crp-f0052/README.md#regression-impact-scope-20261017)、
[F0051 接口澄清](../crp-f0051/README.md#f0051-a-approval-20261017)。

<a id="test-artifacts"></a>
## 修复测试代码与证据的提交范围

来源：用户2026-10-18明确要求，修复相关测试代码只提交必要部分，也可不提交。

1. 验证执行要求不变；测试代码是否入库单独判断。仅有长期回归价值、可维护且适合现有测试入口的最小用例/脚本才随修复提交；没有必要时不提交测试代码，由agent筛选并说明，无须另设确认轮。
2. 一次性host/fake夹具、工具包装、采集脚本、生成的C/h/mk、源码快照、日志/JSON、截图及镜像等默认本地保留，不因后缀可跟踪就批量入库。必要的测试源或文本见证可精确纳入，避免重复副本；提交前核对暂存清单，按需使用仅作用于本批记录目录的忽略规则防止误加。
3. 修复报告保留命令、结果、限制及本地证据入口，继续更新records索引、当前状态和唯一下一入口；不以减少测试代码提交量为由减少必要验证，也不从commit推定本地证据已备份。默认不追溯清理历史已跟踪测试或改全仓跟踪规则；用户明确授权追溯清理时，定向分类、仅移出冗余文件的跟踪并保留本地原文件和字节，不改写历史commit。

<a id="state-closeout"></a>
## 批次留档与状态承接

1. 每个 CCR-F 分别记录修改/未修、失败语义、验收证据与限制；报告留在对应 records 目录，更新 [process 索引](../../../README.md)。历史审阅台账与完成快照保留，不能用历史“未修”截面覆盖当前进展。
2. CURRENT_STATE 更新当前批次、最后完成动作、工作文件、风险及完成/确认/提交状态；Next Action 只指向 TASK_QUEUE 的唯一入口。TASK_QUEUE 同步本批状态，并按上方合批规则维护未来批次的范围、资料、门槛、逐项/共享验收和停点。
3. CHANGELOG_AGENT 按全局持久化规则追加实际完成或补充回执；管理维护只记维护结果，不伪造业务 Phase Completion。DECISIONS 仅新增长期技术裁决时更新，DOCUMENT_INDEX 仅重要导航变化时更新。
4. 完成不等于确认或提交。统一收尾后停止，按全局“每轮执行与提交收尾”处理用户后续提交指令；本地忽略资产不随普通 commit 备份。
